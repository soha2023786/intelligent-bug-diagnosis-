Main Steps
1. Bug Report Submission

The developer submits a bug report containing information such as:

Bug title
Bug description
Stack trace
Error logs
Additional files or supporting information
2. Bug Report Processing

The submitted information is validated, cleaned, and converted into a structured format.

Important information such as error messages, exception types, affected components, and stack traces can be extracted during processing.

3. Error and Stack Trace Analysis

The system analyzes the error logs and stack traces to identify important technical evidence.

Examples include:

Exception types
Error messages
Failed methods
File names
Line numbers
Failure patterns
4. Historical Bug Retrieval

The processed bug report is converted into an embedding and compared with historical defect records.

Historical defects from sources such as Mozilla, Apache, and Eclipse are used as the knowledge base.

5. Similar Bug Identification

Semantic similarity is used to identify historical bug reports that are similar to the newly submitted bug.

This can help identify previously solved or related defects.

6. Root Cause Analysis

The retrieved historical defects, stack traces, logs, and bug description are provided as evidence for root cause analysis.

The system determines the probable reason for the observed failure.

7. Fix Recommendation

Based on the available evidence and historical resolutions, the system provides a possible fix recommendation and debugging steps.

2. Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation, commonly known as RAG, is an approach that combines information retrieval with a Large Language Model (LLM).

Instead of depending only on the knowledge stored in an LLM, the system first retrieves relevant information from an external knowledge base and then provides that information to the LLM as context.

RAG Workflow
New Bug Report
      ↓
Text Processing
      ↓
Embedding Generation
      ↓
Vector Search
      ↓
Retrieve Similar Historical Bugs
      ↓
Build Relevant Context
      ↓
LLM
      ↓
Diagnosis / Recommendation
RAG Components
1. Query

The newly submitted bug report acts as the query.

2. Embedding Generation

The bug report is converted into a numerical vector representation using an embedding model.

3. Retriever

The retriever searches the vector database for historical defect records that are semantically similar to the submitted bug.

4. Retrieved Context

The most relevant historical bug records are selected as context.

5. LLM

The LLM uses the submitted bug and retrieved historical information to generate a diagnosis and possible recommendation.

Advantages of RAG
Uses project-specific historical knowledge.
Reduces dependence on the LLM's internal knowledge.
Helps retrieve previously reported defects.
Provides supporting evidence for diagnosis.
Can improve the relevance of fix recommendations.
Allows the knowledge base to be updated independently.
3. Semantic Similarity

Semantic similarity measures how closely two pieces of text are related in meaning.

In bug diagnosis, two bug reports may describe the same problem using different words.

Example

Bug Report A:

Application crashes when the user opens the profile page.

Historical Bug:

Program terminates unexpectedly while loading user profile information.

Although the wording is different, both descriptions have a similar meaning.

Semantic similarity can help identify this relationship.

4. Text Embeddings

An embedding is a numerical representation of text.

An embedding model converts text into a vector containing numerical values representing information about the meaning of the text.

For example:

Bug Description
       ↓
Embedding Model
       ↓
Numerical Vector
       ↓
[0.21, -0.14, 0.73, 0.08, ...]

For this project, Sentence Transformers are proposed for generating text embeddings.

The initial embedding model selected for the prototype is:

all-MiniLM-L6-v2

The embeddings can be used for semantic similarity and vector search.

5. Vector Search

Vector search is used to find the most similar records based on their vector representations.

The historical defect embeddings are stored in a vector index.

When a new bug is submitted:

New Bug
   ↓
Generate Embedding
   ↓
Compare with Historical Bug Embeddings
   ↓
Calculate Similarity
   ↓
Retrieve Top-K Similar Bugs

The retrieved records can then be passed to the RAG pipeline.

Proposed Vector Search Technology

The initial prototype uses:

FAISS (Facebook AI Similarity Search)

FAISS provides efficient similarity search over numerical vectors and is suitable for experimenting with the historical defect knowledge base.

6. Historical Bug Report Structure

Historical bug reports generally contain multiple fields describing the defect and its lifecycle.

The proposed standardized structure for this project includes:

Field	Description
Bug ID	Unique identifier of the historical defect
Project	Source project such as Mozilla, Apache, or Eclipse
Title	Short description of the bug
Description	Detailed explanation of the defect
Component	Software component affected by the defect
Severity	Impact level of the defect
Priority	Importance or urgency of fixing the defect
Stack Trace	Technical failure trace, if available
Comments	Discussion and additional information
Resolution	Final resolution status
Fix Information	Information about the solution or fix

This common structure allows defect records from different projects to be processed consistently.

8. Data Cleaning and Standardization

Before creating embeddings, historical defect data needs to be cleaned and standardized.

The proposed cleaning process includes:

Removing empty records.
Handling missing values.
Removing exact duplicate records.
Standardizing field names.
Normalizing text formatting.
Removing unnecessary whitespace.
Preserving technical terms.
Preserving exception names.
Preserving stack traces.
Preserving resolution and fix information.

The cleaned records will then be converted into the standardized historical defect schema.

9. Chunking Strategy

Large historical bug reports may contain descriptions, comments, stack traces, and resolution information.

Instead of embedding an entire large record as one piece of text, the information can be divided into meaningful chunks.

The proposed chunk types are:

Description Chunk
Stack Trace Chunk
Comment Chunk
Resolution Chunk
Fix Information Chunk

Each chunk will retain metadata such as:

Bug ID
Project
Component
Severity
Priority
Chunk Type

This allows the system to retrieve specific and relevant information during semantic search.

12. Proposed Approach

The proposed system combines semantic retrieval with an AI-agent-based diagnosis workflow.

The new bug report is first processed and converted into an embedding. The embedding is compared with historical defect embeddings stored in the vector index.

The most relevant historical defects are retrieved and supplied as context to the AI agent layer.

The planned agents include:

Triage Agent
Log Analysis Agent
Duplicate Detection Agent
Root Cause Agent
Remediation Agent

This approach allows the system to use both the newly submitted bug information and historical defect knowledge when producing a diagnosis.
